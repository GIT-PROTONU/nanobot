IMU

roll– pitch– yaw– |accel|– |gyro|– rate– mag xyz– mag magnitude– mag noise (2s)– worst noise seen0.0

Mounting-position interference check (all client-side, no extra load): hold the loose IMU near each candidate spot — motors, ESP32, wiring, metal chassis — and watch mag magnitude/noise; a jump means magnetic or electrical interference there. To find out WHICH nearby part is the culprit, hold it close to one at a time and briefly toggle that part — spin the LDS (Lidar card), flip the cooling fan override (System card), or nudge the drive joystick — watching for a spike here. Worst noise seen peak-holds the biggest jump since the last reset, so you don't have to stare at it while walking the sensor around. Raw sensor counts — useful only to compare spots, not an absolute field reading — but the % next to mag noise IS absolute: wobble as a fraction of the field ≈ 0.6° of heading error per 1%, so ≤ 2% is good for SLAM (≤ ~1° wobble), and past 6% (~3.4°, half the scan-matcher's per-scan correction window) the mount is bad enough to corrupt the map.

Live attitude, rendered client-side (CSS 3D, no extra network/CPU load) from the same roll/pitch/yaw above — the coloured face AND the white ▼ arrow on the roof both mark the front (the arrow stays visible even when the coloured face rotates out of view). Tilt/turn the robot and check the model follows. The small red/green/blue axis triad marks where the IMU itself sits — it's driven by the mount offset fields below, so it sits exactly on the body's centre dot at 0,0,0 and slides out from there as you dial in the real mounting position. Red = IMU X (forward), green = Y (left), blue = Z (up).

The BWT901CL's default 9-axis fusion mixes the magnetometer
              into the reported yaw, so a mag disturbance near motors/LDS/wiring becomes a yaw
              JUMP the scan matcher can't absorb (see the margins above). 6-axis mode drops
              the magnetometer from yaw entirely — heading is gyro-only, trading mag jumps for
              slow gyro drift (which SLAM IS built to absorb). Try it if the mag-noise/drift
              numbers above keep reading red near the chassis. Zero yaw resets the current
              heading to 0° (only meaningful in 6-axis mode). Bandwidth is the sensor's own
              internal vibration filter — lower rejects more motor/chassis noise at the cost of
              response lag; try 10 Hz if numbers are noisy even while genuinely stationary. Always
              Save (above) to persist axis mode to flash.

A DIFFERENT problem from the offset above: the sensor board itself
              glued down at an angle on the chassis (its own "forward"/"up" not lined up with
              the robot's), not moved off-centre. This is the sensor's full fixed orientation —
              a flat sideways twist is yaw only, but a board mounted tipped up on an edge
              needs roll and/or pitch too; the driver properly rotates
              accel/gyro/mag and reconstructs roll/pitch/yaw through the combination, not just a
              yaw shift. To find the right values: rest the robot flat and note the
              roll/pitch/yaw reading above, then prop up ONLY the front (no turning, no
              sideways lean) and see which reported angle actually changes — that tells you
              which of these three fields corresponds to a nose-up tilt; repeat propping up
              ONLY one side to find the other. Whichever reported angle moves for a given
              physical tilt is the one to set (typically 90/-90/180). Leave all at 0 if unsure;
              they default off. Persists across restarts once changed here.

Tests whether the offsets above are actually right (no extra
              hardware or backend needed — reuses the same |accel|/|gyro| stream).
              Spin the robot in place (joystick twist with no forward stick, or run the

              from the true mount point, or a wrong sign) and spin again until it's green. Only
              meaningful for a pure in-place turn — driving forward while turning will show a
              real residual that has nothing to do with the offset.

Continuous on-GPU frame-diff ("PIR") + optional colour-blob
              tracking + luminance, computed whether or not the video view is open (all
              off when gpu_vision_enable is false). Motion center/
              intercept rate are the motion-saliency and kinetic-intercept Tier-B
              extensions. Motion intercept is the same looming-alert math applied to
              raw motion instead of a calibrated target — no colour needs to be set. Lens
              obstructed flags a flat, dark frame (hand/dust over the lens); try covering
              the camera to see it trigger. Colour cast is the scene's average R/G/B —
              watch it shift under different lighting. Visual interest is how much
              texture/contrast is in frame (try pointing at a blank wall vs. a cluttered
              shelf); overhead structure is the same signal cropped to the top of the
              frame (try holding something up high); shiny surface flags specular
              highlights (try a phone screen or mirror); backlit flags a bright spot in
              an otherwise dim scene; focus/blur flags a sudden sharpness drop (try
              covering the lens partially, close up); motion ↔ target shows how close
              the moving thing is to the tracked colour (needs a target calibrated first).
              Pipeline load is a SOFTWARE-measured proxy — the fraction of each frame's
              time budget spent in the shader+readback block; over 100% means the vision loop
              can't keep up with the configured fps and is quietly falling behind (confirmed on
              real hardware — see the gpu-vision-implemented memory). All have live sliders
              under ▸ Vision alerts tuning — thresholds are tuned from real hardware
              readings where available (obstruction's flatness default), otherwise still
              initial guesses. All informational only so far.
              Optical bumper flags commanded-but-not-moving (possible
              wheel stall/slip) — it reads "clear" almost all the time simply because
              the robot isn't currently being driven; commanded /cmd_vel shows
              exactly what it's seeing so that's visible instead of a single opaque
              flag. To actually see it trigger: drive the robot from the Drive
              tab while something blocks a wheel (or just pick it up) — commanded speed
              stays nonzero, GPU motion stays near zero, and after confirm time
              the bumper should flag. Blob tracking tuning: colour match
              tolerance is how close a pixel must be to the calibrated colour to
              count (higher = more forgiving, catches more shades but more false
              positives); min/max blob size gate how much of the frame must match
              to count as a real lock — raise min if a couple of stray pixels are
              triggering a false lock, lower max if the calibrated colour also
              matches a big wall/background area (use the 🎭 Show tracking mask
              button to see exactly what's matching before tuning these). Picking a new
              target colour resets all three to their defaults; glare derating
              scales the lock confidence down when specular highlights fill the frame,
              so a shiny reflection matching the tracked hue can't hold a false lock
              (0 = off). Named targets is the persistent calibration palette —
              every pick is saved under the name typed in the Camera view, survives
              restarts, and can be re-selected or deleted here.
              Novelty compares the scene to a slow ~20 s background average — it
              stays high while something about the room is genuinely different, then
              habituates; camera frozen flags a capture path that stopped
              delivering (or keeps delivering the identical buffer — a USB/driver
              wedge, not a wheel stall); vibration flags an image much blurrier
              while driving than the standing-still baseline (loose screw / wheel
              imbalance — a maintenance hint); approaching fires when motion is
              growing fast AND centred, i.e. someone is walking up to the robot.
              Several signals now have autonomous consumers in the behaviour layer
              (see robot.yaml behavior:): approach → an anticipatory greeting,
              looming/clutter → caution fast-rules (which throttle speed only if
              slam_nav's trait_motion opt-in is on), novelty → a boosted
              "looking" beat, colour cast → the idle face's ambient mood tint, and the
              scene scalars feed a visual diary folded into reflection.
              Dark reflex: opt-in, auto-toggles the ESP32's
              /led from brightness with hysteresis (on/off thresholds must stay
              apart to avoid flicker).

Wheel trim rebalances the mismatched gearmotors so a forward
              command goes straight. If the robot drifts left, push the slider
              negative (boost left / cut right); if it drifts right, push
              positive. The live value (in parentheses) is what the ESP32 is actually
              using and is persisted to its flash, so it survives a reboot — the slider
              re-syncs to it on load. Reset trim to 0 clears the rebalance.

            

              

            
Live from the ESP32 (zenoh-pico over UART). LDS spin telemetry
              + target rpm moved to the Lidar (LDS) card above. The override publishes
              /pickup_override so pick-up-gated behaviour (mood reflex) can be tested
              off the ground; the L/R rows keep showing the real switches.
              Resets to auto on page reload. Stray ticks = ticks the ESP32 counted
              while that wheel was commanded (and settled) stopped — should stay at 0;
              a rising count with the robot motionless means encoder-line noise
              (ground bounce, a loose signal wire), not real rotation. Reset ticks
              zeros both counters (and the stray counters) for a clean baseline —
              odometry re-seeds automatically so /odom doesn't jump. Accel ramp
              caps how fast the applied motor duty may follow a commanded change (duty
              units/sec) instead of stepping straight to it — lower is smoother/gentler
              but laggier, higher is snappier but jerkier. A dead-man stop (lost link/cmd)
              always cuts power immediately, ignoring this ramp.
